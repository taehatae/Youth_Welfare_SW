# 로그인 기반 맞춤형 역설계 안내 구현 계획

## 요구사항 변경: 재인증 제거

이전 구현은 매 요청 아이디·비밀번호 확인과 2분 표시 제한을 사용했다. 아래 기존 설계와 검증 기록은 해당 구현의 이력이다. 현재 사용자의 변경 지시에 따라 맞춤 안내만 로그인 세션 기반으로 전환한다. 별도 프로필 열람의 재인증은 유지한다.

### 현재 적용할 설계

- 전용 `POST /users/condition-guides/view` 경로는 유지한다. 로그인 쿠키와 기존 `current_account`를 사용하며 계정별 snapshot, profile_key, checked_at, policy_id를 검증한다. 아이디·비밀번호는 요청하지 않는다.
- 진단 당시 프로필과 원문·조건 연결 검증 및 안내 생성은 재사용한다. 공개 응답·스냅샷·DB에는 맞춤 문장을 추가하지 않는다.
- 미충족 탭을 열면 자동 조회한다. 임시 메모리만 사용하고 탭 종료·화면 이탈·숨김·로그아웃·계정 전환 시 폐기한다. 초점 복귀 시 다시 인증 조회한다.
- 수동 잠금과 2분 표시 만료를 제거한다. 화면이 계속 활성화된 경우에도 주기적으로 재조회해 서버 세션을 검증하며 실패 시 개인화 내용을 폐기한다. 서버가 외부에서 세션을 만료시키는 순간을 브라우저가 즉시 알 수는 없으므로 재검증 주기를 운영상 한계로 기록한다.
- 다른 탭의 로그인·로그아웃은 개인정보 없는 BroadcastChannel 알림으로 메모리를 폐기한다. 늦은 응답·다른 진단 응답은 세대 번호로 차단한다.
- Cache-Control: no-store 응답과 fetch cache: no-store를 적용한다. 정책 JSON·판정 엔진·DB 스키마는 유지한다.

### 작업 순서

- [x] 로그인만으로 조회, 비로그인·만료·타 계정·스냅샷 혼합 차단 테스트를 먼저 작성하고 실패를 확인한다.
- [x] 전용 요청에서 자격증명 필드를 제거하고 로그인 및 소유권 검증을 유지한다.
- [x] 프런트 자동 조회와 메모리 폐기·늦은 응답 차단을 구현하고 테스트한다.
- [x] 전체 백엔드·프런트 테스트, 타입 검사·빌드, diff 점검 및 보호 파일 해시 비교를 수행한다.

### 로그인 기반 변경 검증 결과

- 전체 백엔드: **814 passed, 882 warnings**. 개인화 전용 테스트 30개는 메모리 DB와 가상 프로필만 사용했다.
- 전체 프런트: **46 passed**. `npx tsc --noEmit`, `npm run build` 통과.
- 자격증명 없는 요청, 세션 만료/로그아웃 후 401, 타 계정/이전 진단/다른 스냅샷 거절, 진단 이후 편집된 프로필과의 혼합 방지를 검증했다.
- 실제 검수 정책 4개의 원문과 가상 입력에서 맞춤 문장·상태/점수/대표 경로·저장 스냅샷 보존을 확인했다. 프로필 원문 열람 재인증은 유지했다.
- 클라이언트의 쿠키·계정 헤더·no-store 요청, 401/계정 변경/타 탭 알림 시 메모리 폐기, 늦은 응답 무효화 및 BroadcastChannel 제한 환경을 검증했다.
- 운영·개발 DB 3개와 `.env`, `backend/data/` 20개 파일의 해시가 작업 전후 동일했다. 외부 API 호출·DB 적재·커밋·푸시는 수행하지 않았다.
- `git diff --check` 통과. 기존 LF/CRLF 변환 경고만 존재한다.
- 브라우저 직접 클릭은 미검증이다. 로그인 → 미충족 탭 자동 안내 → 다른 화면 이동 → 로그아웃/타 탭 계정 변경 → 기본 안내로 전환을 수동 확인해야 한다.
- 서버에서 강제 만료된 세션은 다음 요청에서 차단한다. 열린 화면의 안내는 60초 간격 재검증과 초점 복귀에서 폐기되므로 즉시 서버 알림은 보장하지 않는다. BroadcastChannel 미지원/차단 시 다른 탭 계정 변경도 해당 재검증을 통해 확인한다.

## 이전 재인증 구현 이력

> 구현 방식: 현재 Hwang에서 직접 실행한다. 커밋·푸시·PR은 수행하지 않는다.

## 목표와 보호 경계

사용자가 요청한 A 방식으로, 기존 재인증 규칙을 재사용한다. 기본 진단 응답·저장 스냅샷에는 현재 값이 들어간 문장을 추가하지 않는다. 기존 status, 점수, 대표 경로, checks, 정책 JSON, DB 스키마는 변경하지 않는다.

## 설계

- `POST /users/condition-guides/view`: 로그인 및 매 요청 아이디·비밀번호 검증, 기존 throttle 적용. snapshot, profile_key, checked_at, policy_id를 받아 계정 소유의 해당 진단만 조회한다.
- 현재 검수 경로의 원문 해시와 저장 결과의 대표 경로·조건명·정확한 요구값·근거 구절이 모두 일치하는 단일 조건만 사용한다. required_value를 파싱하지 않는다. 애매하거나 변경된 결과는 기본 안내를 유지한다.
- 실제 비교 함수의 입력 정규화를 재사용하고, 저장된 failed와 현재 비교 의미가 일치하는 경우에만 설명을 생성한다. 이는 기존 결과를 바꾸는 재진단이 아니다. 연도 의존 지표는 진단 연도가 달라지면 보류한다.
- 조회 결과는 저장하지 않는다. 프런트 미충족 카드에서만 일시 사용하고, 2분 만료·blur·숨김·컴포넌트 해제·진단 변경 시 제거한다. 늦게 도착한 응답도 폐기한다.
- 이전 스냅샷·레거시 분석처럼 정확한 구조 연결이 없으면 개인화하지 않는다. 전체 경로 UI는 추가하지 않는다.

- [x] 실제 검수 원문 사례와 합성 조건을 구분해 검증한다. 이전 스냅샷과 기존 조건 안내 테스트를 유지한다.

## 특별 점검

- 월세/전세는 주택 보유나 세대원 전원 무주택의 증명이 아니다.
- 본인 월소득으로 환산한 연소득을 공식 종합소득으로 설명하지 않는다.
- 입력 누락·구간 정보·자유 텍스트·해시 불일치·중복 연결은 개인화하지 않는다.
- 공개 기본 안내는 계속 현재 값과 정확한 차액을 포함하지 않는다.
