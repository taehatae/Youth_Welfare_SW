# 자격 경로 작업 안내 (사람·LLM 공용)

이 문서는 다른 작업자, 또는 작업자가 쓰는 LLM(Claude, GPT 등)이 **이것만 읽고** 자격 경로 데이터 작업을 이어갈 수 있게 쓴 것이다.
LLM에게 일을 시킬 때는 이 문서 전체와 해당 정책 원문을 함께 넣는다. 사람이 볼 판단 기준은 [`REVIEW_GUIDE.md`](REVIEW_GUIDE.md), 설계 배경은 [`README.md`](README.md)에 있다.

## 2. 데이터 흐름과 "한 정책 = 한 곳" 규칙 (중복 방지)

```
welfare-policies.json (정책 원문 152개, API 응답 그대로)
        │
        ├─ eligibility_paths_reviewed.json (사람 검수본 20개)  ─┐  검수본이 있으면 검수본만 쓴다
        └─ structure_gold_*.json (정답지 152개)  ──────────────┘  없으면 정답지를 경로로 변환
                         │  python scripts/build_eligibility_paths.py
                         ▼
        eligibility_paths.json (진단 시드 152개, 정책당 1개)
                         │  python scripts/load_eligibility_paths.py
                         ▼
        DB: policy_eligibility(serv_id 기본키) / eligibility_paths / eligibility_path_conditions
```

중복이 생기지 않는 이유 (테스트로 확인한다: `tests/test_build_eligibility_paths.py`, `tests/test_eligibility_path_service.py`)
- **정답지**: 한 정책은 정답지 파일 4개 중 **한 파일에만** 있다. 같은 serv_id가 두 파일에 있으면 테스트가 실패한다.
- **검수본**: serv_id가 겹치지 않는다. 사람 검수 20개는 정답지에도 있지만, 시드를 만들 때 **검수본이 있으면 정답지는 쓰지 않는다**(둘을 합치지 않음).
- **시드**: 원문 스냅샷의 152개와 정확히 같은 집합이고 정책마다 한 번씩 들어간다.
- **DB**: `serv_id`가 기본키다. 시드를 다시 넣으면 그 정책의 경로를 통째로 지우고 다시 넣는다. 시드에서 빠진 정책은 DB에서 지운다.
- **초안·채점 기록 파일**(`*_batchN_draft.json`, `*_review.json`, `*_fix1_*.json`)은 **기록일 뿐 시드 입력이 아니다.** 여기 있는 정책은 검수본에도 있지만 빌드는 이 파일들을 읽지 않는다.
- **원문 해시**: 검수본은 검수 시점 원문의 해시(`source_sha256`)를 갖는다. 원문이 바뀌면 그 정책은 시드에서 빠지고 `[재검수 필요]`로 출력된다. 바뀐 원문에 예전 검수 결과가 붙지 않는다.

**하지 말 것**
- 검수본(`eligibility_paths_reviewed.json`)을 손으로 고치지 않는다. 고친 초안을 `scripts/merge_reviewed.py`로 합친다. 이 스크립트가 해시와 검수일을 기록한다.
- 같은 정책을 정답지 파일 두 곳에 쓰지 않는다. 검수가 끝난 정책을 정답지에서 지울 필요는 없다(검수본이 우선한다).
- 시드(`eligibility_paths.json`)를 직접 고치지 않는다. 항상 빌드 스크립트로 만든다.

## 3. 차수 하나를 처리하는 순서

```bash
cd backend
# 1) 초안: 아래 4장 프롬프트로 정책 10개 안팎의 초안을 만들어 저장
#    data/eligibility_paths_batch3_draft.json   ({"version":2,"batch":3,"status":"draft","policies":[...]})
python scripts/make_review_sheet.py data/eligibility_paths_batch3_draft.json ../docs/eligibility-paths/batch-3   # 자동 점검
# 2) 사람 채점 (http://localhost:8765). 판단마다 맞음/틀림, 놓친 조건 입력 → data/eligibility_paths_batch3_review.json
python scripts/review_server.py data/eligibility_paths_batch3_draft.json
# 3) 채점대로 초안 수정(5장 프롬프트) → 검수본에 합치기 → 시드 → DB → 테스트
python scripts/merge_reviewed.py data/eligibility_paths_batch3_draft.json
python scripts/build_eligibility_paths.py && python scripts/load_eligibility_paths.py
python -m pytest -q
```
- 차수를 추가하면 `scripts/build_eligibility_paths.py`의 `BATCH_DATES`에 검수일을 적고, `tests/test_review_sheet.py`의 검수본 개수 기대값을 고친다.
- 이미 검수한 정책을 고칠 때(경로 추가 등)는 그 정책만 담은 초안을 만들어 같은 절차를 밟는다. 예: `eligibility_paths_fix1_draft.json`. 이전에 검수한 문구는 채점 화면에서 "기존 검수"로 미리 채워 두고, 새로 생긴 줄만 채점한다.

## 4. 초안 작성 프롬프트

아래 블록을 그대로 LLM에 넣고, 마지막에 정책 원문(serv_id, 정책명, 지원 대상, 선정 기준)을 붙인다.

````text
너는 청년 복지 정책의 자격 조건을 "자격 경로" JSON으로 옮기는 작업자다.
진단 서비스는 사용자가 입력한 값만으로 정책별 신청 가능 / 확인 필요 / 신청 불가를 판정한다.
가장 중요한 원칙: 신청할 수 있는 사람을 "불가"로 판정하게 만드는 조건을 절대 넣지 않는다.
"가능"이 조금 넓게 나오는 것은 괜찮다(확인 사항으로 안내한다).

## 구조
- 정책 하나 = 경로 여러 개. 경로끼리는 "또는"이다(하나만 맞으면 신청 가능).
- 경로 하나 = conditions(입력값과 비교, 모두 맞아야 함) + checks(입력으로 비교할 수 없는 확인 사항, 판정에 안 씀).
- common / common_checks = 모든 경로에 공통인 조건 / 확인 사항.
- preferences = 가점·우선선발. 판정에 안 씀.
- 조건이 하나도 없는 경로가 있으면 그 정책은 불가가 되지 않는다. 원문에 "그 밖의 사람"처럼 조건 없는 대상이 있으면 그런 경로를 둔다.

## 출력 형식 (정책마다)
{"serv_id": "...", "name": "...",
 "common": [조건...], "common_checks": ["..."],
 "paths": [{"id": "짧은-식별자", "label": "화면에 보일 이름", "kind": "기본|유형|순위|예외", "priority": 1,
            "conditions": [조건...], "checks": ["..."]}],
 "preferences": ["..."]}
조건 = {"field": 입력 항목, "op": "gte|lte|between|one_of|is_true", "value": 숫자, "upper": 숫자(between),
        "values": [문자열](one_of), "kind": "requirement|exclusion"(기본 requirement),
        "evidence": "원문에서 그대로 복사한 근거 구절"}
- evidence는 원문 글자 그대로여야 한다(띄어쓰기 차이는 허용, 떨어진 구절은 "..."로 잇는다). 자동 점검이 원문에 있는지 확인한다.
- exclusion은 "해당하면 제외"다. 예: {"field":"본인 명의 주택 보유","op":"is_true","kind":"exclusion"}.
- priority는 kind가 "순위"일 때만 쓴다.

## 입력 항목(field)과 값
수치(op: gte/lte/between):
  만 나이(세) · 본인 월소득(원) · 본인 연소득(원, 월소득×12) · 가구원 수(명) · 자녀 수(명)
  가구 소득인정액(기준 중위소득 대비 %, 재산 환산 포함) · 가구 월소득 중위소득 대비(%, 소득만. 원문이 '가구 소득'이면 이것)
  도시근로자 월평균소득 대비 가구소득(%)
  가구 총재산(원, 함께 사는 가구 전체) · 본인 총재산(원, 본인 명의. 1인 가구면 가구 총재산과 같음)
  가구 순자산(원, 가구 총재산 − 가구 부채) · 본인 순자산(원, 본인 재산 − 본인 부채). 원문이 '순자산'이면 이것
  부부합산 연소득(원, (본인+배우자 월소득)×12. 미혼은 본인 연소득) · 자동차가액(원, 가구)
  혼인 기간(년) · 신용점수(KCB)(점) · 신용점수(NICE)(점)
선택(op: one_of):
  고용 상태: 재직 | 중소기업 재직 | 아르바이트 | 미취업 | 자영업 | 프리랜서
  혼인 상태: 미혼 | 기혼 | 이혼 | 사별
  주거 형태: 자가 | 전세 | 월세 | 무상 거주 | 기타
  국적: 대한민국 | 외국인
  성별: 남성 | 여성
  거주지: "시도" 또는 "시도 시군구" (예: "경상남도", "서울특별시 성동구")
  학교 구분: 고등학교 | 대학 | 대학원 (재학 중일 때만. 전문대·산업대·원격대는 "대학")
예/아니오(op: is_true):
  재학 여부(입학·복학 예정 포함) · 등록 장애인 · 중증 장애인(장애의 정도가 심한) · 본인 명의 주택 보유 · 세대원 전원 무주택 · 부모와 따로 거주
  기초생활보장 수급자(본인) · 기초생활보장 수급 가구(본인 또는 가구 내 수급자) · 생계급여 수급자 · 의료급여 수급자 · 주거급여 수급자 · 교육급여 수급자
  차상위계층 · 한부모가족 · 자립준비청년 · 국가유공자·보훈대상자(본인 또는 자녀) · 북한이탈주민 · 결혼이민자·다문화가족 · 농업인·어업인
  맞벌이(기혼이고 본인·배우자 모두 소득) · 6세 이하 자녀 · 임신 중(본인 또는 배우자) · 구직 등록
이 목록에 없는 것(성적, 학년, 최종 학력, 재직 기간, 연매출, 업종, 거주 기간 등)은 조건이 아니라 checks에 문장으로 쓴다.
목록에 있는 기준은 반드시 비교 조건으로 쓴다(확인 사항으로 남기지 않는다). 비교할 수 있는 조건이 많을수록 판정이 의미 있다.

## 판단 규칙
1. 입력으로 비교할 수 있는 조건은 반드시 conditions에 넣는다. 확인 사항으로만 두지 않는다.
2. 누구 기준인지 맞춘다. 원문이 본인 기준이면 본인 월소득·본인 총재산, 세대·가구 기준이면 가구 항목.
   부모와 사는 청년을 가구 기준으로 비교하면 잘못 불가가 된다.
3. 기준이 가구 형태마다 달라지면(맞벌이/외벌이 × 가구원 수 등) conditions에서 빼고 형태별 기준표를 checks에 쓴다.
4. 원문 조건이 입력보다 세밀하면 꼭 필요한 부분만 조건으로 둔다. 예: "중증 장애인" → 조건 "등록 장애인" + 확인 "중증일 것".
5. 대상을 넓히는 단서를 놓치지 않는다: "입학 예정 포함", "신청 월에 만 40세가 되는 자", "태아 포함", "임신 중", "※" 단서.
   넓히는 단서 때문에 조건이 안 맞을 수 있으면 그 조건을 빼거나 넓은 값으로 바꾼다.
6. "또는"은 경로를 나눠 표현한다. 유형(1형/2형, 일반/청년/신혼 등)이 다르면 조건이 같아 보여도 유형별로 나눈다.
7. 상위 순위에 해당하지 않아야 하는 하위 순위("1·2순위에 해당하지 아니하는 사람")는 checks에 "○순위에 해당하지 않을 것"을 쓴다.
8. 모든 경로에 같은 조건이 있으면 common으로 올린다. 경로마다 기준이 조금 다르면 가장 넓은 값을 common에 두고 좁은 값은 checks에 쓴다.
9. 조건과 checks가 모두 같은 경로는 하나로 합치고 label에 유형을 함께 적는다. 조건이 같아도 checks가 다르면 나눠 둔다.
10. checks에 원문 어디를 말하는지 모를 일반론("공고 기준 확인")을 쓰지 않는다. 실제 기준을 해당 경로에 쓴다.
11. 금액·수치 기준을 하나도 빠뜨리지 않는다. 경로가 여러 개면 경로마다 확인한다(예: 자동차가액은 checks).
12. 대상 설명은 원문 표현대로 쓴다. 예: "구직자일 것"(X) → "저소득 구직자·청년·경력단절여성 등 취업 취약계층일 것"(O).
13. 숫자 단위: 금액은 원 단위 정수(3억 4,500만원 → 345000000), 비율은 % 숫자(중위소득 50% 이하 → lte 50). 미만은 1을 빼서 lte로(270만원 미만 → lte 2699999).

## 마지막으로 스스로 점검
- 원문의 모든 대상 유형이 경로로 들어갔는가? 빠진 유형이 없는가?
- 어떤 경로든 "원문상 대상인데 조건 때문에 불가"가 되는 사람이 없는가? (예정자, 태아, 부모 동거, 프리랜서, 학점은행제 등)
- 모든 evidence가 원문에 글자 그대로 있는가?
JSON만 출력한다.
````

## 5. 채점 결과 반영 프롬프트

````text
아래는 자격 경로 초안 JSON과, 사람이 채점 화면에서 남긴 결과(*_review.json)다.
review의 items 키는 "경로id|c번호"(조건), "경로id|k번호"(확인 사항), "_pref|번호"(우대), 공통은 "_common|..."이다.
ok=false인 항목은 note대로 고치고, missing(놓친 조건)은 알맞은 경로·확인 사항으로 추가한다.
고칠 때도 4장의 판단 규칙을 지킨다(특히 잘못된 불가 금지). note가 판정 규칙과 부딪히면 고치지 말고 이유를 따로 적는다.
고친 초안 JSON과, 항목별로 무엇을 어떻게 고쳤는지 목록을 출력한다.
````

## 6. 정답지 형식 (검수 전 132개가 쓰는 형식)

`structure_gold_*.json`은 경로 이전의 단순한 형식이다. 빌드 스크립트가 경로로 바꾼다.
```jsonc
{"WLF00006290": {"name": "경남동행론(직접대출)",
  "required": [{"field": "거주지", "op": "one_of", "values": ["경상남도"]},   // 모든 신청자에게 필요한 조건(AND)
               {"field": "본인 연소득", "op": "max", "value": 35000000}]},
 "WLF00006224": {"name": "저소득층 수도요금감면", "required": [],
  "or": [[{"field": "만 나이", "op": "min", "value": 65}, {"field": "등록 장애인", "op": "is_true"},   // 묶음 중 하나만 맞으면 됨
          {"field": "기초생활보장 수급자", "op": "is_true"}, {"field": "차상위계층", "op": "is_true"}]]}}
```
- 연산자 이름이 다르다: `min`=gte, `max`=lte, `range`=between. 근거 구절(evidence)이 없다.
- 변환하면 `required` → 공통 조건, `or` 묶음의 선택지 하나 → 경로 하나(묶음이 여러 개면 조합마다 경로)가 된다.
- 잘못된 불가를 막기 위해 `or`는 **모든 선택지를 입력으로 비교할 수 있을 때만** 썼다. 선택지 중 하나라도 입력이 없으면(예: 미소금융 "신용평점 하위 20%") 묶음을 넣지 않았다.
- 정답지 정책을 검수할 때는 정답지를 고치지 말고, 4장 프롬프트로 **경로 초안을 새로 만들어** 검수 절차를 밟는다.

## 7. 판정 규칙 요약 (엔진: `backend/app/services/eligibility_path_service.py`)

| 단위 | 규칙 |
|---|---|
| 조건 | 충족 / 미충족 / 미입력. exclusion은 해당하면 미충족 |
| 경로 | 미충족이 하나라도 있으면 불가. 비교 조건이 모두 충족이면 가능. 그 밖(미입력, 비교 조건 없음)은 확인 필요 |
| 정책 | 가능한 경로가 하나라도 있으면 가능, 모든 경로가 불가면 불가, 그 밖은 확인 필요 |
| 확인 사항 | 판정을 바꾸지 않는다. 화면의 "추가 확인"에 나온다 |
| 대표 경로 | 상태 → 미충족 적은 순 → 미입력 적은 순 → 충족 많은 순 |

설정: `backend/.env`의 `USE_ELIGIBILITY_PATHS=true`, `USE_STRUCTURED_CONDITIONS=true`. 둘 다 기본값은 꺼짐이다.
원문 해시(DB 원문 기준)가 시드와 다르면 그 정책은 경로 판정을 쓰지 않고 기존 분석으로 돌아간다.

## 8. 검증 방법

- 자동: `python -m pytest -q`로 데이터 중복, 근거 구절, 해시, 판정을 확인한다.
- 판정 확인: 프로필 5~6개(부모 동거 대학생, 1인 직장인, 수급·장애, 미입력 많음, 경계 나이, 외국인 등)를 정한다. **엔진을 돌리기 전에** 원문만 보고 정책마다 기대 결과를 적은 뒤 비교한다. 가장 먼저 셀 것은 잘못된 불가(목표 0건)다.
- 지금까지 결과: 1차 50/50, 2차 59/60(틀린 1건은 허용한 넓은 가능). 새로 정답지를 쓴 57개는 프로필 6개 × 57개의 불가 128건을 원문과 대조했고, 모두 원문상 맞는 불가였다.
