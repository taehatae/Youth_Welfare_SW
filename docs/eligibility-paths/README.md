# 자격 경로(Eligibility Path) 설계안

> 검수 방법과 판단 기준은 [`REVIEW_GUIDE.md`](REVIEW_GUIDE.md), 작업을 이어받는 사람·LLM용 안내(현재 상태, 데이터 흐름, 중복 방지 규칙, 작업 프롬프트)는 [`LLM_GUIDE.md`](LLM_GUIDE.md)에 있다. 이 문서는 데이터 형식·판정 규칙 설계안이다.

> 목표: 프론트에서 입력한 값만으로 정책 자격을 **정확하게** 판정하고, 신청 불가인 정책은 **무엇이 부족한지(역설계)** 보여준다.

## 1. 왜 바꾸나

지금 구조화 데이터(`backend/data/structured_conditions.json`)는 정책마다 **조건 목록 하나(AND) + '또는' 묶음 하나**뿐이다.
정책 원문은 대부분 "유형·대상마다 다른 조건"으로 되어 있어서 이 구조로는 표현이 안 된다.

| 원문 | 지금 구조의 한계 |
|---|---|
| 진단서 발급비: ① 신규 등록이 필요한 **수급자** ② 재판정 대상 **등록 장애인** 중 수급자·차상위 | "수급자 또는 차상위" 하나로 뭉개져, 장애인이 아닌 차상위도 '신청 가능'으로 나옴 |
| 공공분양: 일반 100%, 생애최초·신혼 130%, 노부모·다자녀 120%, 그 외 소득 기준 없음 | 유형마다 달라서 소득 조건을 통째로 버림 → 비교할 조건 거의 없음 |
| 장애인활동지원: 6~64세 등록장애인 / 65세 도래 예외 / 퇴소 예정 | 나이 조건을 버림 |
| 국가유공자 대부: 주택 대부만 세대 무주택 | 무주택 조건을 버림 → 역설계 불가 |

결과적으로 95개 중 30개 정책이 "비교할 조건 0개"가 됐고, 1차 사람 검수에서 이견도 대부분 이 지점(유형별·순위별 조건)에서 나왔다.

## 2. 데이터 형식

정책 → **경로 여러 개(이 중 하나만 맞으면 신청 가능)** → 경로마다 조건(모두 맞아야 함).

```jsonc
{
  "serv_id": "WLF00000057",
  "name": "공공분양",
  "source_sha256": "...",            // 원문 해시. 원문이 바뀌면 재검수 대상
  "common": [ /* 모든 경로에 공통인 비교 조건 */ ],
  "common_checks": [ "해당 주택건설지역에 거주할 것" ],   // 입력으로 비교 못 하는 공통 확인 사항
  "paths": [
    {
      "id": "생애최초", "label": "생애최초 특별공급",
      "kind": "유형",                 // 기본 | 유형 | 순위 | 예외
      "priority": null,               // 순위 경로면 1, 2, 3
      "conditions": [                 // 입력값과 비교하는 조건 (AND)
        { "field": "도시근로자 월평균소득 대비 가구소득", "op": "lte", "value": 130,
          "kind": "requirement",      // requirement | exclusion
          "evidence": "생애최초 특별공급 ... 130% 이하" }   // 원문 근거 구절
      ],
      "checks": [ "생애 처음 주택을 구입할 것" ]          // 이 경로의 비교 불가 확인 사항
    }
  ],
  "preferences": [ "취업취약계층 우선 선발(가점)" ]      // 판정에 쓰지 않는 우대 사항
}
```

- **조건(`conditions`)**: 진단 입력 항목(`field`)과 비교 가능한 것만. 연산자는 `gte / lte / between / one_of / is_true`.
- **확인 사항(`checks`)**: 질병, 심사, 공고문 기준처럼 입력으로 판정할 수 없는 것. 판정에는 쓰지 않고 안내만 한다.
- **우대(`preferences`)**: 가점·우선 선발. 판정에 쓰지 않는다.
- '또는'은 경로를 나눠서 표현한다(공공산림: '실업자' 경로 / '정기소득 없음' 경로). 따로 '또는 묶음' 개념이 필요 없다.

전체 예시: [`sample.json`](sample.json) (1차 사람 검수한 정책 10개)

## 3. DB 테이블 (원문 테이블은 그대로 둔다)

```
welfare_services (기존, 수정 없음)  ── API 원문

policy_eligibility                  ── 정책별 구조화 상태
  serv_id (PK, FK)  source_sha256  status(draft|reviewed|stale)
  drafted_by(llm 모델명)  reviewed_by  reviewed_at  version  common_checks(JSON)  preferences(JSON)

eligibility_path                    ── 자격 경로
  id (PK)  serv_id (FK)  path_key  label  kind  priority  sort_order  checks(JSON)
  (공통 조건은 path_key='_common' 경로로 저장)

eligibility_condition               ── 경로별 비교 조건
  id (PK)  path_id (FK)  field  operator  value  upper_value  values(JSON)  kind  evidence
```

- 동기화 때 원문 해시가 바뀌면 `status=stale` → 진단에서는 기존 분석으로 대체하고 재검수 목록에 올린다.
- `status=reviewed`인 정책만 진단에 쓴다.

## 4. 판정 규칙

| 단위 | 규칙 |
|---|---|
| 조건 | 충족 / 미충족 / 미입력 |
| 경로 | 미충족이 하나라도 있으면 **불가**, 비교 조건이 모두 충족이면 **가능**, 그 밖(미입력이 있거나 비교 조건이 없음)은 **확인 필요** |
| 정책 | 가능한 경로가 하나라도 있으면 **가능**, 모든 경로가 불가면 **불가**, 그 밖은 **확인 필요** |

- 확인 사항(`checks`)은 상태를 바꾸지 않는다(모든 정책에 심사·서류 확인이 있으므로 이걸로 막으면 아무것도 '가능'이 안 됨).
- **신청 가능한 사람을 '불가'로 판정하는 오류가 가장 위험**하다. 그래서 비교 조건이 없는 경로가 하나라도 있으면 그 정책은 절대 '불가'가 되지 않는다(매입임대 청년 3순위, 암환자 건강보험 기준 등).

### 화면 표시 (3단계)

- **신청 가능**: 어떤 경로로 가능한지 표시 ("'생애최초 특별공급' 경로 충족") + 그 경로의 확인 사항
- **확인 필요**: 무엇을 입력하면 판정되는지 표시 ("세대원 전원 무주택 입력 필요")
- **신청 불가**: 역설계 (아래)

### 역설계

- 모든 경로가 같은 **공통 조건**에서 막히면 → "모든 경로 공통: 등록 장애인 필요"
- 아니면 **미충족이 가장 적은 경로**를 '가장 가까운 경로'로 → "가장 가까운 경로 '실업자': 고용 상태 미취업 필요(현재 중소기업 재직)"
- 나중에: 미충족 조건이 바꿀 수 있는 것(소득·재산·고용)인지, 바꿀 수 없는 것(나이·장애)인지 구분해서 안내

## 5. 검증 결과 (프로토타입)

1차 사람 검수한 정책 10개를 경로 형식으로 옮기고, 테스트 프로필 5개(프론트 실제 입력 변환 코드 `toProfile` 사용)로 판정했다.
기대 결과는 데이터와 별개로 정책 원문을 읽고 정했다.

| 방식 | 일치 |
|---|---|
| 지금 구조 (가능/불가 2단계) | 49/50 — 진단서 발급비에서 '장애인 아닌 차상위'를 가능으로 잘못 판정 |
| **자격 경로 (3단계)** | **50/50** |

상세: [`prototype-result.md`](prototype-result.md)

프로필: A 대학생 알바 / B 장애인 생계·의료급여 수급자 / C 주택 보유 직장인·유공자 자녀 / D 외국인 유학생 차상위 / E 자영업·미확인 많음

## 6. 구조화 파이프라인

```
API 원문 ─▶ ① LLM 초안(경로·조건·근거 구절) ─▶ ② 클로드 원문 대조·수정, 애매한 곳 표시
        ─▶ ③ 사람 검수(애매 표시 + 무작위 표본) ─▶ ④ reviewed로 DB 저장 ─▶ 진단
원문 변경(해시 불일치) ─▶ stale ─▶ ①부터 다시
```

- 로컬 LLM(Qwen 2.5 14B) 단독 정확도는 정책 단위 약 70%(검증용 30개)라 초안 용도로만 쓴다.
- 사람 검수는 채점 화면에서 **판단 하나하나를 맞음/틀림으로 채점하고 놓친 조건을 적는** 방식으로 한다([`REVIEW_GUIDE.md`](REVIEW_GUIDE.md)).
- 판정 기준(검수 기준)을 먼저 합의한다: 모든 신청자 공통이 아니면 경로로 나누고, 순위는 `kind=순위`, 가점은 `preferences`.

## 7. 정확도 측정

- **데이터 정확도**: 검수하지 않은 정책에서 무작위 20~30개를 뽑아 2명이 경로 단위로 채점.
- **조회 정확도(목표에 직접 대응)**: 대표 프로필 8~10개 × 무작위 정책 30개에 대해 사람이 기대 결과(가능/확인 필요/불가)를 적고, 시스템 결과와 비교. 이번 프로토타입 검증을 확장한 형태.
- 오류는 종류별로 센다: **잘못된 불가**(목표 0건) / 잘못된 가능 / 불필요한 확인 필요.

## 8. 입력 항목 과제 (경로 작업 중 발견)

| 부족한 입력 | 영향 받는 예 |
|---|---|
| ~~재학 상태 세분화(재학·휴학·입학 예정·졸업)~~ | 재학 여부 칸에 "입학·복학 예정이어도 '해당'" 안내 문구로 해결 |
| ~~본인 명의 재산~~ | 추가함. 행복주택 대학생·청년 경로가 본인 기준 자산으로 비교 |
| 맞벌이 여부 | 공공분양·행복주택 등 4개 정책. 가구 형태별 기준이라 지금은 확인 사항 |
| 해당 대상 체크박스의 '모름' | 지금은 아무것도 안 고르면 '해당 없음'으로 판정 |
| 원가구(부모) 소득·재산 | 청년월세, 매입임대 청년형 |
| 혼인 기간, 자녀 나이, 임신 여부 | 신혼부부·다자녀 특별공급, 농식품바우처 |
| 장애 정도(중증/경증) | 가스·전기요금 할인 |

경로가 늘어나면 "이 입력만 있으면 판정되는 경로"를 셀 수 있으므로, 입력 추가 우선순위를 데이터로 정할 수 있다.

## 9. 진행 순서 (제안)

1. 이 설계안 백엔드 담당자와 합의 (특히 3장 테이블, 4장 3단계 상태)
2. 판정기(`eligibility_path_service`)와 테이블 구현, 기존 `structured_condition_service`는 경로 데이터가 없을 때 대체용으로 유지
3. 95개 정책을 경로 형식으로 이전 (현재 데이터 + 원문 재검토)
4. 프론트: 3단계 결과 + 경로 표시 + 역설계 문구
5. 조회 정확도 측정(7장) → 입력 항목 보강(8장) → 나머지 정책 동기화

## 열린 질문

- '확인 필요'를 결과 화면에서 별도 탭으로 둘지, '신청 가능' 안에 표시할지
- 순위 경로(1·2·3순위)를 사용자에게 "몇 순위로 신청 가능"까지 보여줄지
- 공고마다 바뀌는 기준(도시근로자 소득표, 자산 기준)의 연도 관리 방식
